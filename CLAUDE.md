# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **native macOS app** (AppKit + SwiftUI, Swift 6) that provides a Finder-style GUI for the `sbx` CLI (Docker-backed sandbox manager for AI agents). It is a ground-up rewrite of the Tauri 2 + Vue 3 app in `../sbx-ui`; domain knowledge (exact `sbx` invocations, macOS PATH fix, agent-launch env convention) was ported from `../sbx-ui/src-tauri/src/sbx.rs`. Terminals are rendered with **libghostty**. The app is **not App-Sandboxed** (`ENABLE_APP_SANDBOX: NO`) — required for libghostty to spawn real PTY subprocesses.

## Build & run

The Xcode project is generated by **XcodeGen** from `project.yml` — never edit `Sandshell.xcodeproj` by hand.

```bash
xcodegen generate                        # regenerate after editing project.yml

# Debug build (arm64)
xcodebuild -project Sandshell.xcodeproj -scheme Sandshell \
  -configuration Debug -derivedDataPath build \
  -destination 'platform=macOS,arch=arm64' build

open build/Build/Products/Debug/Sandshell.app   # launch via path (proves PATH fix works)

# Release build
xcodebuild -project Sandshell.xcodeproj -scheme Sandshell \
  -configuration Release -derivedDataPath build-release \
  -destination 'platform=macOS,arch=arm64' build
```

First build resolves the `libghostty-spm` SwiftPM package and downloads the xcframework.

### Release

```bash
scripts/release.sh <version>    # e.g. scripts/release.sh 0.2.14
```

Bumps `MARKETING_VERSION` in `project.yml` → regenerates → Release build → DMG via `scripts/make-dmg.sh` → uploads via `gws`. Requires `xcodegen` and `gws`.

## Tests

UI tests are AppleScript-based (no XCTest/unit tests exist):

```bash
scripts/run-ui-tests.sh                 # build + run all tests
scripts/run-ui-tests.sh --skip-build    # reuse last Debug build
scripts/run-ui-tests.sh --force-quit    # quit running Sandshell first
scripts/run-ui-tests.sh --keep-open     # leave app open after tests
```

Tests live in `tests/ui/`. The runner launches Sandshell via `sandshell://open?workspace=…`, then drives it with `osascript`. Requires `sbx` on PATH.

## Architecture

### Layer overview

```
AppDelegate (@main)
  └─ MainWindowController (per workspace root; NSWindow + NSSplitViewController)
       ├─ SidebarOutlineController   NSOutlineView; folder/session tree
       └─ TerminalStackController    detail pane; hosts live TerminalSession views
  └─ WorkspaceController (@MainActor ObservableObject)   central state coordinator
       ├─ Workspace          value type: rootURL, policy, mcpServers, primaryAgent, kits
       ├─ WorkspaceState     persisted: folders, sessions, tree expansion (state.json)
       ├─ WorkspaceConfig    persisted: mounts, theme, MCP, kits
       └─ SbxClient (actor) shells out to `sbx` CLI
```

### Key source files

| File | Role |
|------|------|
| `App/AppDelegate.swift` | `@main`; patches PATH, creates/restores `MainWindowController` windows, handles Apple Events (`Shll`/`stat`, `Shll`/`news`) and URL scheme (`sandshell://open`), global keyboard shortcuts |
| `UI/MainWindowController.swift` | NSWindow + `NSSplitViewController` (sidebar \| detail); native toolbar; theme observation |
| `UI/TerminalStackController.swift` | Detail pane; owns and displays live `TerminalSession` views |
| `Sbx/WorkspaceController.swift` | Central `@MainActor` coordinator: container phases, session list, selection, runtimes, MCP state — observed by sidebar, detail, and toolbar |
| `Sbx/SbxClient.swift` | `actor`; all `sbx` CLI calls via `Process` (async/await). `sbx create` uses a temp file for stderr (not a pipe) to avoid stalling Foundation's FileHandle callback queue |
| `Sbx/Models.swift` | `Sandbox`, `AgentKind`, `CreateOptions`, `CommandOutput` |
| `Sbx/Workspace.swift` | `Workspace` value type + `MountSpec` parser/renderer |
| `Sbx/MountPolicy.swift` | Mount selections, seed agent mounts, resolve with cap |
| `Sbx/PathFixer.swift` | Login-shell PATH probe + `setenv`; resolves `sbx`/`docker`/`brew` for GUI-launched app and libghostty subprocesses |
| `Terminal/TerminalSession.swift` | One libghostty `TerminalController` + `AppTerminalView` per live session; writes a temp `#!/bin/sh` launch script |
| `Terminal/SbxCommand.swift` | Builds the `sbx exec … env … bash -c '…'` launch script body |
| `Workspace/WorkspaceState.swift` | Persisted folder+session tree (`state.json`) |
| `Workspace/WorkspaceConfig.swift` | Persisted workspace config (mounts, theme, MCP, kits) |
| `Workspace/HistoryStore.swift` | Past conversation history browser |
| `Theme/ThemeController.swift` | Per-window `ThemePreferences` + resolved `ThemeColors` |

### Key quirks

- **One window per workspace root.** `AppDelegate` manages an array of `MainWindowController` instances. Multiple windows on the same root are allowed (cascaded).
- **WorkspaceController is the single source of truth.** Container phases, sessions, runtimes, and MCP state all live here; UI observes `@Published` properties.
- **SbxClient stderr quirk.** `sbx create` spawns a long-lived daemon that inherits pipe fds, so stderr capture uses a temp file to avoid stalling the shared `FileHandle` callback queue.
- **libghostty terminal per session.** Each `TerminalSession` owns a `TerminalController` (one ghostty "app"). Command is set via a temp executable script — never via config-file quoting. Backend must be `.exec` (real PTY).
- **PATH fix.** `PathFixer.patchProcessPath()` runs at launch; the fixed environment is inherited by libghostty's subprocesses too.
- **Apple Event scripting API.** The companion CLI (`scripts/sandshell`) queries status as JSON and opens new sessions via custom Apple Events. The `sandshell://open?workspace=…&ro=…&rw=…` URL scheme is also handled in `AppDelegate`.
- **Appearance.** `UIDesignRequiresCompatibility = true` in Info.plist opts out of macOS 26 Tahoe Liquid Glass (renders as Sequoia style).
- **XcodeGen is the source of truth.** `project.yml` controls everything: targets, build settings, `MARKETING_VERSION`, post-build copy of `scripts/sandshell` into the bundle.

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/SYNC_CONCEPTS.md for details and anti-patterns.

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, and orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.
