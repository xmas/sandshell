# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A **native macOS app** (AppKit + SwiftUI, Swift 6) that provides a Finder-style GUI for the `sbx` CLI (Docker-backed sandbox manager for AI agents). It is a ground-up rewrite of the Tauri 2 + Vue 3 app in `../sbx-ui`; domain knowledge (exact `sbx` invocations, macOS PATH fix, agent-launch env convention) was ported from `../sbx-ui/src-tauri/src/sbx.rs`. Terminals are rendered with **libghostty**. The app is **not App-Sandboxed** (`ENABLE_APP_SANDBOX: NO`) — required for libghostty to spawn real PTY subprocesses.

## Build & run

The Xcode project is generated by **XcodeGen** from `project.yml` — never edit `Sandshell.xcodeproj` by hand.

```bash
xcodegen generate                        # regenerate after editing project.yml

# Debug build (arm64)
xcodebuild -project Sandshell.xcodeproj -scheme Sandshell \
  -configuration Debug -derivedDataPath build \
  -destination 'platform=macOS,arch=arm64' build

open build/Build/Products/Debug/Sandshell.app   # launch via path (proves PATH fix works)

# Release build
xcodebuild -project Sandshell.xcodeproj -scheme Sandshell \
  -configuration Release -derivedDataPath build-release \
  -destination 'platform=macOS,arch=arm64' build
```

First build resolves the `libghostty-spm` SwiftPM package and downloads the xcframework.

### Release

```bash
scripts/release.sh --dry-run <version>   # rehearse: real build + DMG, prints publish commands, changes nothing
scripts/release.sh <version>             # e.g. scripts/release.sh 0.2.20
```

Distributed via the Homebrew tap `xmas/xmas` (public repo `xmas/homebrew-xmas`): `brew install --cask xmas/xmas/sandshell`. The script preflights (main, clean tree, gh auth, tap clone at `../homebrew-xmas` clean on main) → bumps `MARKETING_VERSION` → regenerates → Release build → DMG via `scripts/make-dmg.sh` → sha256 → `gh release create sandshell-v<version> -R xmas/homebrew-xmas` with the DMG → updates + pushes `Casks/sandshell.rb` in the tap → commits the bump, tags `v<version>`, pushes. Release notes come from the `## v<version>` section of `CHANGELOG.md`. Requires `xcodegen` and `gh`. The in-app updater (`Sandshell/Update/Updater.swift`) reads the version from the raw cask on GitHub. Details: `RELEASING.md`.

## Tests

### Unit tests (Swift Testing)

```bash
scripts/run-unit-tests.sh                    # build + run every suite (xcodebuild test, build-tests/)
scripts/run-unit-tests.sh AgentQuestionTests # only these suites/tests
```

`tests/SandshellTests` (target `SandshellTests`, mirrors the source folders) tests the app's core logic with Swift Testing — parsing, coding, scripts, path and git handling. It's hosted in the app, which opens no windows and touches no sandboxes when it sees it's hosting tests (`AppDelegate.isHostingTests`). Write new tests per the swift-testing-pro skill: structs, `#expect`/`#require`, parameterized where it fits, temp dirs for anything on disk, never the user's home, `UserDefaults.standard`, `~/.claude` or sbx. A production bug a test exposes is a bead (and a `withKnownIssue` until fixed).

### UI tests

UI tests are AppleScript-based:

```bash
scripts/run-ui-tests.sh                 # build + run all tests
scripts/run-ui-tests.sh --skip-build    # reuse last Debug build
scripts/run-ui-tests.sh --force-quit    # quit running Sandshell first
scripts/run-ui-tests.sh --keep-open     # leave app open after tests
```

Tests live in `tests/ui/`. The runner launches a headless test copy (own bundle id, transparent click-through windows), opens a temp workspace through the file-based test bridge, then drives it with `osascript`. Requires `sbx` on PATH. Settings tests use the bridge's in-app `ax` commands (`App/UITestAX.swift`), so the suite also runs with the screen locked. Details: `tests/ui/README.md`.

### DEBUG self-tests

```bash
scripts/run-self-tests.sh                # every scenario, each on a fixture made fresh (≈30–60 min)
scripts/run-self-tests.sh --quick        # no agent turns, no sandboxes created from scratch
scripts/run-self-tests.sh --only files,commits --skip-build
```

The runner builds the dev bundle, makes or resets each scenario's fixture under `/tmp/sandshell-selftests` (`scripts/selftest_fixtures.py`: git repos, session lists in `state.json`, kit dirs, removed sandboxes), runs it, and prints a summary (results in `<root>/results/<time>/<scenario>/`). Add a scenario's fixture there when you add a scenario.

Scripted end-to-end checks inside the real app (`App/SelfTest.swift`): launch a Debug binary with `-SandshellSelfTest <scenario> -SandshellSelfTestOut <dir> -openWindowRoots '("<workspace>")'`; it drives the window offscreen (transparent, click-through, never activates), writes PASS/FAIL lines to `<dir>/selftest.log` plus snapshots, and quits. Scenarios: `panes`, `pane-buttons`, `files-alone`, `files`, `files-relaunch`, `chat`, `fork`, `follow`, `links`, `open-quickly`, `title-strip`, `building`, `alerts`, `background`, `sandbox-access`, `launch-failure`, `kits`, `agents`, `search`, `sidebar`, `remote` — each documents the workspace fixture it expects. Build a separate bundle id for these (`PRODUCT_BUNDLE_IDENTIFIER=com.xmas.sandshell.dev`, `-derivedDataPath build-dev`) so they don't touch your own app's defaults. Chat scenarios use the signed-in account (a few tiny turns).

**No dialogs during tests**: `Diagnostics/AutomatedRun.swift` is active under `-SandshellSelfTest` / `-SandshellUITestHeadless` — no Keychain or notification prompts, alerts answer themselves, destructive steps only for `/tmp` scratch workspaces.

## Architecture

### Layer overview

```
AppDelegate (@main)
  └─ MainWindowController (per workspace root; NSWindow + NSSplitViewController)
       ├─ SidebarOutlineController   NSOutlineView; flat session list
       ├─ PaneTreeController         detail: a split tree of panes, saved per window
       │    ├─ TerminalStackController   one pane: a session's terminal or chat
       │    └─ SessionSurfaces           the window's live terminals + chats, shared by its panes
       └─ FilesPaneController        trailing inspector: file tree + editor (never a pane)
  └─ WorkspaceController (@MainActor ObservableObject)   central state coordinator
       ├─ Workspace          value type: rootURL, policy, mcpServers, primaryAgent, kits
       ├─ WorkspaceState     persisted: folders, sessions, tree expansion (state.json)
       ├─ WorkspaceConfig    persisted: mounts, theme, MCP, kits
       └─ SbxClient (actor) shells out to `sbx` CLI
```

### Key quirks

- **One window per workspace root.** `AppDelegate` manages an array of `MainWindowController` instances. Multiple windows on the same root are allowed (cascaded).
- **WorkspaceController is the single source of truth.** Container phases, sessions, runtimes, and MCP state all live here; UI observes `@Published` properties.
- **SbxClient stderr quirk.** `sbx create` spawns a long-lived daemon that inherits pipe fds, so stderr capture uses a temp file to avoid stalling the shared `FileHandle` callback queue.
- **Chat is the default.** ⌘N and + ▸ New Claude/Codex/Gemini start a chat (ACP adapter in the sandbox via `sbx exec -i`); terminal versions sit under + ▸ In Terminal, and each pane's title strip switches Chat ⇄ Terminal (`Session.isChat`).
- **Session processes are tagged.** Agents launched in a sandbox carry `SANDSHELL_SESSION`/`SANDSHELL_LAUNCH` env and are reaped on close/restart/quit (`SbxClient.reapSessionProcesses`).
- **Panes reparent live views.** After moving a libghostty view between panes call `setSurfaceVisible(false)` then `(true)` or it won't draw.
- **libghostty terminal per session.** Each `TerminalSession` owns a `TerminalController` (one ghostty "app"). Command is set via a temp executable script — never via config-file quoting. Backend must be `.exec` (real PTY).
- **PATH fix.** `PathFixer.patchProcessPath()` runs at launch; the fixed environment is inherited by libghostty's subprocesses too.
- **Apple Event scripting API.** The companion CLI (`scripts/sandshell`) queries status as JSON and opens new sessions via custom Apple Events. The `sandshell://open?workspace=…&ro=…&rw=…` URL scheme is also handled in `AppDelegate`.
- **Appearance.** `UIDesignRequiresCompatibility = true` in Info.plist opts out of macOS 26 Tahoe Liquid Glass (renders as Sequoia style).
- **XcodeGen is the source of truth.** `project.yml` controls everything: targets, build settings, `MARKETING_VERSION`, post-build copy of `scripts/sandshell` into the bundle.

## Sandshell's kits

`kits/` holds Sandshell's own sbx kits, bundled in the app (`Contents/Resources/kits`) and published to the public repo `xmas/sandshell-kits` on release (`scripts/publish-kits.sh`):

- `sandshell-claude` (claude sandboxes): preinstalls the Claude ACP adapter and `sandshell-acp.mjs`, a wrapper that adds rewind (Undo) and MCP status/reconnect/toggle on the adapter's `_session/async_task/stop` request (`asyncTaskId` `sandshell:<base64url JSON>`).
- `sandshell-codex` (codex sandboxes): preinstalls codex-acp and writes Codex's proxy sign-in placeholder.

Workspaces reference them by name (`KitStore.sandshellKits`); `KitStore.resolve` turns that into the bundled path for sbx. They're on by default (added once per workspace, `sandshellKitsOffered`), don't count toward the create signature or kit drift (existing sandboxes get them at their next rebuild), and the chat shows Undo/MCP only when the launch reports the wrapper (`sandshell-extras: on`). sbx only allows `docker.io/` and `github.com/docker/` kit sources by default, so the published git refs need `kit.allowedSources` to include `github.com/xmas/`.

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol
- Use `bd remember` for persistent knowledge — do NOT use MEMORY.md files

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/SYNC_CONCEPTS.md for details and anti-patterns.

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, and orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.
